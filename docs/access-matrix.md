# Матриця доступу ЛР 4 - Incident, baseline 2-A

Рівень виконання - відмінний. Рішення приймає лише сервер для комбінації
суб'єкт + дія + ресурс + контекст. Суб'єкт і роль беруться тільки з verified
principal (claim `NameIdentifier` і server-issued role claim після login),
власник і статус - тільки зі збереженого `Incident`. Поля `ownerUserId`, `role`,
`status` або інші прапорці з body, query чи заголовків не є входом рішення.

Роль Administrator не має прав над інцидентами, яких предметне правило 2-A
прямо не називає. Тому Administrator працює з інцидентами так само, як Reporter
(лише як власник власних записів), без адміністративного обходу ownership.

Severity і status не входять до DTO звичайного update. Статус змінює лише сервер
у transition triage після перевірки поточного стану. Severity після створення
не змінюється жодною роллю, бо предметне правило 2-A такої дії не публікує.

## Політика HTTP-відмов

| Ситуація                                                                      | Відповідь                                                                         |
| ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Немає verified principal                                                      | 401 Problem Details, без HTML redirect                                            |
| Principal не має права бачити інцидент (чужий для Reporter або Administrator) | 404 Problem Details `Інцидент не знайдено`, однаковий для чужого й неіснуючого id |
| Principal бачить інцидент, але дія для нього заборонена                       | 403 Problem Details `Forbidden`                                                   |
| Дозволений суб'єкт, але поточний статус не допускає transition                | 409 Problem Details                                                               |

Обґрунтування. Для Reporter чужий інцидент є чужими даними, тож сам факт його
існування не має розкриватися. Тому для details, update, delete, triage і
коментарів чужого інциденту обрано 404, і відповідь не відрізняється від
відповіді для неіснуючого id ні статусом, ні Content-Type, ні тілом (крім
`traceId`). Порядок перевірки однаковий у всіх маршрутах: спершу право Read на
ресурс, потім право на конкретну дію. Якщо Read дозволено, існування ресурсу
вже не секрет, тому відмова в дії - 403. Так власник, якому заборонено triage,
і Analyst, якому заборонено update чи delete, одержують зрозумілу явну відмову.

Найменші привілеї (least privilege). Reporter має рівно ті права, без яких не може вести власні
повідомлення - створити, прочитати, виправити текст і відкликати ще не
опрацьоване (статус New). Analyst читає всі інциденти, бо без цього неможлива
класифікація, і має лише один змінювальний дозвіл New -> Triaged. Content
update і delete Analyst не потрібні для класифікації, тому заборонені.
Administrator не одержує невизначених правил, бо предметна область 2-A не
публікує для нього адміністративних операцій над інцидентами.
